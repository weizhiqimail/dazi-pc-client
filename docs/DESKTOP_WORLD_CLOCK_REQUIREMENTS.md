## 1. 改造目标

将当前的 Dazi Toolkit 工具箱改造成一个 Windows 桌面多时区时钟。

它不是传统的大型多页面应用，而是一个尺寸很小、可长期停靠在桌面边缘的桌面挂件。用户可以同时查看多个城市的当地日期、24 小时时间，以及这些城市相对某个基准城市早或晚多少小时。

核心体验目标：

- 小巧、低干扰，适合长时间停留在桌面上。
- 可停靠在屏幕左侧、右侧或顶部。
- 可锁定位置，避免误拖动。
- 关闭主窗口后仍可驻留 Windows 系统托盘，并通过托盘菜单重新打开或设置。
- 界面采用古老、朴素、死板的 Windows 桌面软件风格，不使用现代卡片、动画、毛玻璃、圆角、阴影或图标化导航风格。
- 首版只做多时区时钟，不保留现有 Markdown 和工具箱演示功能。

## 2. 已明确的功能需求

### 2.1 应用形态

- Windows 桌面应用。
- 主窗口为小型时钟挂件，不再是当前的大尺寸工具箱页面。
- 支持把窗口放置或停靠在桌面左侧、右侧、顶部。
- 支持锁定窗口。
- Windows 任务栏右下角通知区域显示应用小图标，即系统托盘图标。
- 提供设置入口。
- 支持同时显示多个地区。
- 多个地区支持横向排列或纵向排列，排列方式可配置。

### 2.2 城市与时区

首批内置可选城市：

| 城市 | IANA 时区标识 | 说明 |
| --- | --- | --- |
| 上海 | `Asia/Shanghai` | 中国标准时间 |
| 东京 | `Asia/Tokyo` | 日本标准时间 |
| 纽约 | `America/New_York` | 自动处理夏令时 |
| 芝加哥 | `America/Chicago` | 自动处理夏令时 |
| 洛杉矶 | `America/Los_Angeles` | 自动处理夏令时 |
| 伦敦 | `Europe/London` | 自动处理夏令时 |
| 巴黎 | `Europe/Paris` | 自动处理夏令时 |

城市是配置项，用户可以选择显示其中一个或多个，并调整显示顺序。

### 2.3 时间显示

- 所有时间均使用 24 小时制。
- 每个城市显示当地当天日期。
- 每个城市显示当地当前时间。
- 用户可以选择一个已显示城市作为基准城市。
- 其他城市显示相对基准城市“早 N 小时”或“晚 N 小时”。
- 时差必须按当前日期下的真实 UTC 偏移量计算，不能写死。纽约、芝加哥、洛杉矶、伦敦、巴黎存在夏令时，时差会随日期变化。
- 时间应自动更新，无需手动刷新。

建议的单项显示结构：

```text
上海
2026-09-24
21:35:08
基准
```

```text
纽约
2026-09-24
08:35:08
晚 13 小时
```

单个地区目标尺寸约为 100 px × 50 px，但这只是用户给出的量级参考。日期、秒数和时差同时显示时，100×50 可能过于拥挤，最终尺寸需要结合字号与信息取舍确认。

### 2.4 设置能力

设置至少需要覆盖：

- 启用或停用城市。
- 调整城市显示顺序。
- 选择基准城市。
- 选择横向或纵向排列。
- 选择窗口停靠位置：左侧、右侧、顶部；是否还提供自由位置需确认。
- 锁定或解锁窗口位置。

### 2.5 托盘行为

- 应用启动后创建系统托盘图标。
- 托盘图标右键菜单至少应考虑：显示/隐藏时钟、设置、锁定/解锁、退出。
- 点击窗口关闭按钮时，是隐藏到托盘还是彻底退出，属于待确认项。
- 应用必须提供明确的“退出”命令，否则驻留托盘后用户难以真正结束进程。

## 3. 明确移除的内容

以下内容从产品中移除，而不是仅从导航中隐藏：

- Markdown 编辑、预览、导出及相关依赖和 IPC 能力。
- 现有工具箱首页、导航实验页、控件实验页、动画页、反馈页等演示内容。
- 现有侧边栏、命令面板、面包屑、大页面布局。
- 现有 Windows 11 / Fluent 倾向的视觉风格。
- 主题、内容宽度、导航字号等与新时钟无关的设置。

是否完整删除尚未使用但与时钟无关的通用组件，应在实施阶段按引用关系清理，并保证没有死代码和无效依赖。

## 4. 视觉与交互方向

目标风格是“传统 Windows 桌面程序”，不是复刻 Windows 11，也不是网页仪表盘。

建议采用以下视觉约束：

- 使用系统字体，例如 Segoe UI、Tahoma 或 Microsoft Sans Serif。
- 方形边框和按钮；最多使用极小圆角，默认无圆角。
- 使用浅灰窗口底色、深灰边框、传统按钮和表单控件观感。
- 不使用渐变、毛玻璃、投影、大面积强调色、卡片悬浮效果。
- 不使用过渡动画和页面切换动画。
- 不依赖现代 UI 组件库。
- 设置界面可采用传统对话框布局：分组框、标签、复选框、下拉框、列表、上移/下移按钮、“确定 / 取消 / 应用”。
- 时钟主窗口信息密度高，但文字必须清晰，不因追求 100×50 而截断日期或城市名。

这里的“原生 Windows UI”存在两种可能解释，必须确认：

1. **视觉原生**：保留 Electron + React 技术栈，但只用 HTML/CSS 模拟传统 Win32 控件风格。这是对当前项目改造成本最低的方案。
2. **技术原生**：弃用 Electron 前端界面，改为 Win32、WinForms、WPF 等真正的 Windows 原生控件。这相当于重写项目，安装包体积、技术栈和后续维护方式都会变化。

当前仓库是 Electron 项目。除非产品方明确选择“技术原生”，建议默认采用“视觉原生”，同时充分使用 Electron 的原生窗口、托盘和菜单能力。

## 5. 时间与数据实现约束

- 如果指定使用 Moment 体系，应使用 `moment-timezone`，而不只是 `moment`。
- 时区必须存储为 IANA 时区标识，不能只存 `UTC+8` 一类固定偏移。
- 时差文案应由目标城市当前 UTC 偏移减去基准城市当前 UTC 偏移得到。
- 需要定义半小时、45 分钟时区的未来显示规则。即使首批城市都是整点时差，数据模型也不应假设时差永远是整数小时。
- 时间来自本机系统时钟；首版不要求联网校时，除非另行确认。
- 配置应持久化到本机，并在下次启动时恢复。
- 对损坏或旧版本配置应有默认值回退，不能导致应用无法打开。

## 11. 建议的首版默认方案

若产品方希望减少确认成本，可直接批准以下默认方案：

- 保留 Electron + React，仅在视觉与交互上采用传统 Windows 风格，不引入 UI 组件库。
- 使用 `moment-timezone` 处理时间和夏令时。
- 时间格式为 `HH:mm:ss`，日期格式为 `YYYY-MM-DD`，城市名使用中文。
- 基准城市显示“基准”，其他城市显示“早/晚 N 小时”；未来遇到非整点时差则显示“N 小时 M 分钟”。
- 主窗口按内容自动调整尺寸；单个时钟块以可读性优先，100×50 作为紧凑目标而非硬限制。
- 横向单行或纵向单列排列，不自动换行。
- 默认右侧边缘吸附，不占用 Windows 工作区；允许拖动到任意位置并吸附左、右、顶部。
- 主窗口不进入普通任务栏，仅显示系统托盘图标。
- 默认不始终置顶、首次不锁定；设置中可以开启置顶和锁定。
- 锁定后禁止拖动和缩放，但托盘菜单仍可解锁和打开设置。
- 点击关闭按钮隐藏到托盘；托盘菜单提供显示/隐藏、设置、锁定/解锁、退出。
- 记忆窗口位置、停靠边、锁定状态、布局、基准城市、启用城市及顺序。
- 设置使用独立传统对话框，提供“确定 / 取消 / 应用 / 恢复默认”。
- 暂不支持开机启动、网络校时、任意新增城市、配置同步、透明度、深色主题和自动更新。
- 首版支持 Windows 10/11 x64，沿用 NSIS 安装包。

## 12. 验收标准草案

### 12.1 核心显示

- 启动应用后能看到配置的全部城市。
- 每个城市显示正确的当地日期和 24 小时时间。
- 时间持续更新，跨分钟、跨日后显示正确。
- 美国和欧洲城市在夏令时切换前后显示正确。
- 更换基准城市后，所有相对时差立即正确更新。

### 12.2 配置

- 能启用、停用和排序城市。
- 能切换横向、纵向布局。
- 能选择基准城市，且基准城市必须是已启用城市。
- 设置在应用重启后保留。
- 配置异常时可以恢复默认设置并正常启动。

### 12.3 桌面窗口

- 窗口可移动到并吸附于规定的桌面边缘。
- 锁定后不会因普通鼠标操作被误移动或缩放。
- 多显示器变化后窗口不会永久停留在不可见区域。
- 横向和纵向布局下窗口均不会裁切城市信息。

### 12.4 托盘与生命周期

- 托盘图标在应用运行时存在。
- 可以从托盘显示或隐藏主窗口、打开设置、锁定或解锁、退出。
- 关闭主窗口后的行为与最终确认一致。
- 重复启动应用不会产生多个时钟实例，而是唤起已有实例。

### 12.5 清理与质量

- 产品界面中不存在 Markdown 和原工具箱功能入口。
- Markdown 相关源代码、配置、IPC 和依赖按引用关系安全移除。
- 不新增现代 UI 组件库。
- TypeScript 类型检查、Lint、测试和 Windows 打包通过。

## 13. 当前仓库影响分析

当前仓库的基础技术栈是 Electron 37、React 19、TypeScript、Vite 和 Less。现有实现与新需求的主要差异如下：

- `src/main/index.ts` 当前只创建一个 1180×760 的普通主窗口，没有托盘、吸附、锁定、窗口状态持久化或设置窗口。
- `src/renderer/App.tsx` 当前是侧边栏加路由页面的工具箱外壳，需要替换为时钟主界面。
- `src/renderer/pages/MarkdownPage`、`src/renderer/helpers/markdown`、`src/renderer/config/markdown.config.ts` 及 Markdown 导出 IPC 属于明确移除范围。
- `markdown-it`、`@types/markdown-it` 和 `lucide-react` 在清理引用后可能都可以移除。
- 当前设置模型围绕主题、密度、内容宽度和字号，需要改成城市、基准时区、布局和窗口行为设置。
- 当前使用浏览器 `localStorage` 保存部分设置。窗口位置、锁定、开机启动等主进程级设置更适合由主进程统一持久化，并通过受限 IPC 暴露。
- 当前自定义隐藏标题栏带有偏现代的 Windows 风格；主时钟窗口和设置窗口需要分别重新定义窗口装饰策略。
- 单实例锁已有基础实现，可以保留并调整为第二次启动时显示现有时钟。

## 14. 后续 Agent 实施指令

在产品方回答关键待确认项或批准第 11 节默认方案前，不修改业务代码。

进入实现阶段后，Agent 应遵守：

1. 先根据确认结果更新本文档，将已决问题从“待确认”改为明确规格。
2. 只实现确认后的首版范围，不擅自增加天气、闹钟、秒表、网络同步等功能。
3. 优先保留当前 Electron 工程和安全边界：`contextIsolation: true`、`nodeIntegration: false`、受限 preload API。
4. 时区逻辑与界面分离，并为夏令时、跨日、基准切换和配置迁移编写测试。
5. 使用 Electron 原生 `Tray`、`Menu`、窗口 API 实现系统能力。
6. 不引入 UI 组件库；传统风格使用少量自有 React 组件和 CSS/Less 实现。
7. 删除功能前先核对引用，避免误删用户无关改动。
8. 实现完成后依次验证类型检查、Lint、测试、生产构建和 Windows 打包。
9. 实机验证托盘、窗口吸附、锁定、多显示器恢复和 DPI 缩放，这些能力不能只靠单元测试确认。
